## 1. 数据库安全性 ⭐

- **课堂概念**：自主存取控制（GRANT/REVOKE）、角色、视图、审计。
- **我们做了什么**：运行时角色 `kv_app`（`NOSUPERUSER` / `NOBYPASSRLS`，无 DDL）；18 张表启用行级安全策略；每请求在事务内 `set_config('app.user_id')`；跨用户读只走 `SECURITY DEFINER` 函数；SQL 练习用独立只读库 + 2 秒语句超时。
- **30 秒讲法**：“我们没有把权限写在每个查询的 WHERE 里，而是建了一个普通数据库角色，给它开行级安全策略。应用连的就是这个角色，所以哪怕代码漏写了条件，数据库也只返回 0 行；越权写入直接 42501。练习用的沙箱是另一个库 + 只读角色，连业务库的 CONNECT 都被收回了。”
- **现场命令**：
  ```bash
  npm run verify:invariants           # E10：带 user_id 的新表必须启用 RLS
  npm run security:audit              # 6 项自查：角色属性、RLS、沙箱隔离、口令哈希、.env、SQL 拼接
  npm test -- tests/security.test.ts  # 越权读写
  npm test -- tests/injection.test.ts # 6 组注入 payload：通配符转义、' OR 1=1 --、DROP/TRUNCATE 不执行
  ```
- **额外一句话**：“我们自己拿注入串打过自己的接口：`%`、`_` 被转义；`'; DROP TABLE messages; --` 只当普通文本，表还在、行数不变。”
  `docs/sql/rls.md` 里有 psql 演示脚本（换用户查表返回 0 行、越权写入 42501）。
- **可能被追问**：“性能怎么办？” → 策略只比较当前行，`user_id` 上有索引；单条查询实测仍在毫秒级；也可以对只读路径用 `security_invoker` 视图。

## 2. 数据库完整性 ⭐

- **课堂概念**：实体完整性（主键）、参照完整性（外键）、用户定义完整性（CHECK、触发器）。
- **我们做了什么**：92 个外键（38 CASCADE / 30 RESTRICT / 20 SET NULL / 4 NO ACTION）；44 个业务 CHECK；5 组复合外键保证冗余列一致；本命花环形引用用 `DEFERRABLE` 外键 + 延迟约束触发器；共学名额用触发器锁行计数。
- **30 秒讲法**：“完整性我们分三层：主键外键是第一层，CHECK 是第二层，跨行规则用触发器是第三层。比如‘本命花必须属于本星球’是跨表规则，我们用可延迟外键把它放到事务提交时检查；‘共学小组不能超员’用 `FOR UPDATE` 锁小组行再计数，6 个并发请求只成功 1 个。”
- **现场命令**：`npm run verify:invariants`（15 项：阶段与证据一致、评价与作答一一对应、幂等键唯一、本命花归属…）。
- **可能被追问**：“约束多了会不会影响性能？” → 外键只在写入时检查，读取不加锁；触发器只挂在 3 张敏感/共享表上；必要时用 `NOT VALID` 先加约束、再 `VALIDATE`。

## 3. 过程化 SQL / 存储过程 ⭐

- **课堂概念**：PL/pgSQL、游标/循环、异常处理、触发器与存储过程。
- **我们做了什么**：
  - `fn_settle_attempt(...)`：锁作答 → 幂等复查 → 写评价/证据/阶段/成长事件/outbox，异常整笔回滚；
  - `fn_audit_row()`：通用审计触发器，记录 actor、表名、操作、变更前后镜像；
  - 增量统计触发器：班级人数/分享数/活跃时间按增量维护，配套对账函数。
- **30 秒讲法**：“作答结算原来在应用里写了七八条 SQL，中间任何一步失败都要靠事务回滚。我们把整段规则写成数据库函数：函数里 `FOR UPDATE` 锁住作答、再查一次幂等、写评价、写证据、重算阶段、写事件和 outbox。应用只调用一次函数，原子性由数据库保证；并发重复提交只结算一次。”
- **现场命令**：
  ```bash
  npm test -- tests/settle-function.test.ts   # 并发 5 次只结算 1 次、重复幂等键 23505、不存在作答 P0002
  npm run bench:batch -- --rows 50000         # 逐行 vs 存储过程 vs 集合操作
  ```
- **性能数字**（本机实测，5000 行更新）：应用逐条 4.1 s → PL/pgSQL 游标 133 ms（省掉往返，约 37×）→ 一条集合 UPDATE 51 ms（再 2.3×）。
- **可能被追问**：“逻辑放数据库里不好维护吧？” → 只有‘必须原子、必须所有写入路径都遵守’的规则才下沉；文案与题型规则仍留在应用层。

## 4. 扩展 SQL ⭐（最容易讲、也最像课程作业）

- **课堂概念**：递归查询、窗口函数、`GROUP BY` 扩展（ROLLUP/CUBE/GROUPING SETS）、`FILTER`、CTE。
- **我们做了什么**：
  - **学习路线规划** `fn_plan_path`：递归 CTE 求先修闭包 → 按到目标的距离倒排（拓扑序）→ 同层按阶段与错题数加权，返回“下一步学什么、为什么”；
  - **学习周报**：`generate_series` 补零、`FILTER` 漏斗、`GROUPING SETS` 学科小计+合计、`percent_rank()` 班级百分位、gaps-and-islands 算连续学习天数。
- **30 秒讲法**：“这两个功能都是用一条 SQL 算出来的。路线规划先把目标的所有先修展开，再按‘离目标多远’排序，保证先修一定排在后面前；同一层里按你现在的阶段和错题数排序。周报更典型：连续学习天数用‘日期减行号’分组，一次算出当前连续和最长连续；学科汇总用 GROUPING SETS 一条语句同时得到分学科和合计。”
- **界面入口**（答辩演示用）：顶栏「成长」→「学习路线」/「学习周报」；手机端在底部导航「成长」。
- **现场命令**：
  ```bash
  npm run plan -- --handle demo --goal 贝叶斯公式
  npm run report -- --handle demo --days 30
  ```
- **截图**：`docs/screenshots/ui/ui-14-plan.png`、`ui-15-report.png`、`ui-16-report-sql.png`（展开 SQL 说明）、`ui-17-mobile-plan.png`。
- **可能被追问**：“先修有环怎么办？” → 数据库触发器用递归 CTE 检测环，插入即报 23514，所以规划器可以放心用递归。

## 5. 数据库编程 ⭐

- **课堂概念**：应用与数据库的接口、事务边界、参数化查询、错误处理。
- **我们做了什么**：统一 `authed()` 入口注入用户上下文；`q()`/`withTx()` 两个访问收口；所有 SQL 用 `$1..$n` 参数化；业务错误码统一（`42501`/`23505`/`P0002` 等）；幂等键 + 唯一索引兜底；模型调用放在事务外。
- **30 秒讲法**：“我们把数据库访问收敛到两个函数：单条查询和短事务。事务里只放数据库操作，模型调用、文件解析放事务外；所有 SQL 参数化；并发冲突靠唯一索引和幂等键，而不是靠应用层判断。”
- **现场命令**：`npm test`（180 个测试（94 集成 + 86 单元），真实 PostgreSQL）。

## 7. 关系数据理论（范式）⭐

- **结论**：48 张表——**40 张 BCNF**；4 张 2NF（`learning_states`、`notes`、`attempts`、`growth_events`）；4 张 1NF（`messages`、`concept_suggestions`、`message_citations`、`learning_evidence`）。
- **8 处受控冗余**：都是把 `user_id`（归属用户）或展示文案冗余进子表，换高频查询少一次 JOIN / 少一层权限判断；每处配复合外键或不变量（E4/E5/E12/E13）兜底。
- **4NF / 5NF**：别名与先修拆成两张表，不存在非平凡多值依赖；没有三元连接依赖，不涉及 5NF。
- **现场**：`npm run docs:keys`（48 张表候选键）；`npm run verify:invariants`（15 项 0 错误）。
- **一句话**：“范式是设计工具，不是教条；我们保留了 8 处冗余，但每一处都能证明它不会坏。”
- 详见 `docs/schema/normalization-analysis.md`。

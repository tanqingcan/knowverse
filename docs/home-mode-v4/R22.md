# R22 花圃变换持久化

> 状态：**第一遍待审**（基础设施完整落地；端到端被 R19/R21 的 M 确认回归阻塞）

## 一、研究
- **布局持久化沿用 `planet_layouts` 行级快照**（与 V3 的 items 同一套乐观并发 revision）。
- 关键取舍：**花圃位移不塞进 `planet_layout_items`**。items 的 `kind` 有 CHECK 约束（只允许素材 kind），把花圃当 item 需要新增 kind + garden_id 列 + 改约束；而花圃位移本质是"每圃一个变换"，用 `planet_layouts.bed_moves` jsonb 更贴合，也不会污染素材 items。
- **球面 vs 平面**：位移存的是球冠平面坐标 (x,z) + rot，与 items 同一坐标系，还原时直接喂给 `layoutBeds` 的 moves 覆盖。

## 二、第一遍实现
1. `schema.ts`：`planetLayouts.bedMoves = jsonb("bed_moves")`。
2. 迁移 `0009_far_human_fly.sql`：`ALTER TABLE "planet_layouts" ADD COLUMN "bed_moves" jsonb;`（已生成并应用）。
3. `server/layouts.ts`：
   - `getLayout` 的 SELECT 增加 `bed_moves AS "bedMoves"`，返回值带 `bedMoves`（默认 `{}`）；
   - `saveDraft(user, baseRevision, items, bedMoves?)` 增加第 4 参；
   - 新增 `cleanBedMoves()`：键必须匹配 `^[A-Za-z0-9_-]{1,64}$`（gardenId 形态）、x/z 在 -6..6、rot 在 -3600..3600，否则 400；
   - INSERT/UPDATE 写 `bed_moves`。
4. API `route.ts`：zod 增加 `bedMoves: record(key, {x,z,rot?}).nullish()` 并透传。
5. `layout-api.ts`：`LayoutResponse.bedMoves` + `saveLayout(baseRevision, list, bedMoves?)`。
6. `SpaceApp`：两处 `loadLayout()` 后 `setBedMoves(l.bedMoves)`；两处 `saveLayout(...)` 带上 `bedMoves`。

## 三、审查（第一遍真实失败）
1. **[高] 端到端未闭环**：本轮测试中 `M → 点目标` 没有确认（热栏仍显示"点击星球表面确定花圃新位置"），所以花圃从未真正移动，`bed_moves` 写进去是 `{}`。这是 R19/R21 的 M 确认路径在最近两轮改动后出现的回归，必须先修才能验证"保存→刷新→还原"。
2. **[中] 未验证独立浏览器上下文**：R22 要求"另一个独立上下文同账号也相同"，本轮未跑。
3. **[中] "layoutBeds 不得覆盖手动摆放"**：当前实现上 `moves` 覆盖优先于默认槽位 ✓（代码层面成立），但没有专门用例。
4. **[中] "新增知识点在当前花圃附近分配"**：未实现（新增植物仍按 gardenIndex 进对应圃的环位）。

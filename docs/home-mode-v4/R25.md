# R25 地形方案比较（球面高度场 vs 装饰山）

> 状态：**第一遍待审**（方案比较已完成并定案；"隔离预览跑通"尚未做——本轮只到方案层）

## 一、三个候选方案

| 方案 | 做法 | 能否满足「真正高山突起 + 池塘凹陷」 | 主要问题 |
|---|---|---|---|
| **A. 球面高度场（顶点位移）** | 把星球 `SphereGeometry` 的顶点按高度场位移；高度存稀疏控制点/低分辨率网格，渲染时双线性插值到顶点 | ✅ 能（顶点真抬起/凹陷） | 拾取与贴地要跟着改；每笔要重建/更新几何；需要把"cap 坐标 ↔ 高度"统一 |
| **B. 纯装饰山模型** | 往场景里放"山"的 mesh，不改星球表面 | ❌ 不能（用户站在球面上，山只是摆件；池塘无法凹陷） | 明确只能当原型，不得标地形完成 |
| **C. 地形补丁（局部 patch 网格）** | 在需要起伏的区域盖一块细分单面网格，与球面在大范围上贴合 | 🟡 局部能（补丁边缘与球面接缝要处理） | 接缝/法线/拾取三处都要特殊处理；补丁外仍是球面 |

## 二、对比结论

- **选 A（球面高度场）**：只有它能同时满足"高山隆起 + 池塘凹陷 + 保持球体拓扑"。
- B 只保留为**原型/降级**（万一 A 性能不达标时的演示），但绝不标"地形完成"。
- C 作为 A 的**局部 LOD 优化**候选（远处用低分辨率，近处补丁细分），一期不做。

**球面 vs 平面差异（关键）**：平面 heightfield 是规则网格索引；本项目的"地形坐标"是**球冠平面坐标 (x,z)**，高度必须与既有的 `capFrame` / `rayToCap` / `worldToCap` 共用一套映射，否则会出现"山抬起来了但物件还在旧球面、点击拾取落在旧表面"的双轨问题。

## 三、实施计划（A 方案）

1. **数据结构**：`heights: Float32Array`（低分辨率网格，例如 64×32 覆盖球冠 ±3 的范围）+ 版本号；保存时序列化为稀疏（只存非零）JSONB，避免每帧传大网格。
2. **几何**：`SphereGeometry` 的顶点做径向位移 `r = R * (1 + h(x,z)/R)`；顶点数与高度网格解耦（插值）。
3. **统一采样**：新增 `terrainHeight(x,z)`（纯函数，插值），供 `capFrame` 的 lift、拾取（射线先与"带高度的球"近似求交，再迭代校正）、物件贴地共用。
4. **笔刷**：抬高/降低/平滑/恢复，半径/强度/柔边；一次点击一笔，写进 `heights` 并入 undo；Esc 退出工具不误放素材。
5. **水面**：盆地 + 一个受盆地边界约束的圆盘/环带水面 mesh（不穿出球面）。
6. **持久化**：`planet_layouts.terrain`（jsonb，稀疏高度 + 版本），与 bedMoves/items 并列。
7. **性能**：每笔只更新受影响顶点（局部 buffer 更新），不重建整个几何；记录 FPS/draw/tri 与 geometries/textures 增量。

## 四、风险与边界

- **拾取精度**：抬升后 `rayToCap` 的"理想球求交"会偏高——需要按高度迭代校正（2–3 次即可），否则 R17 的 ≤8px 误差会退化。
- **既有物件贴地**：所有地面物件/花圃/道路/路径都要经 `terrainHeight` 重新采样，否则会出现悬空/埋入（R28 明确要求）。
- **性能**：6K 顶点以内可接受；若超过，先降网格分辨率再考虑 LOD。
- **权限**：地形属于布局，沿用同一套 owner + revision 校验（R30 的"另一账号不允许改地形"）。

## 五、隔离预览方案

在 `/dev/garden`（已有开发路由）里挂一个**独立的最小场景**：只有星球 + 高度场 + 两个笔刷按钮，不接布局/保存/其他编辑能力。目的是**先验证 A 方案的几何/拾取/性能可行**，再往创造模式里接。

### H52 复制产生独立 ID；原建筑不会再次从默认常量补出来；撤销与回滚准确

- **要求**：复制产生独立 ID，原建筑不会再次从默认常量补出来；撤销与回滚准确。
- **前置依赖**：H03/H06（初始实例与复制）、H12（历史）。

#### GitHub 候选对比与已读源码
- 编辑器/场景序列化的通用原则：**「已保存的场景」是权威**，模板只在**首次创建**时用；一旦进入用户数据阶段，任何"缺少某类对象就补模板"的兜底都会把用户的删除操作吃掉。
- 本项目原有兜底：`serverHasBuildings=false` → 走 `DEFAULT_HOME_LAYOUT` 迁移分支——这对「v2 旧布局」是对的，但对「v3 用户故意删光建筑」就是错的。

#### 第一遍实现（核查 + 加版本字段）
- `planet_layouts` 新增 **`schema_version`**（默认 1 = 迁移前；保存时写 2 = v3 全场景布局），迁移 **`0008_skinny_jocasta`**。
- 服务端 `getLayout` 返回 `schemaVersion`，`saveDraft` 的 INSERT/UPDATE 置 2。
- 客户端加载：**`schemaVersion >= 2` 时直接用服务端 items**（不再走「缺建筑就补模板」的迁移兜底）。

#### 第一遍审查（主动构造失败）
1. **[高] 删光建筑后会被模板补回**：构造「保存一份没有建筑的布局 → 刷新」，旧逻辑会因 `serverHasBuildings=false` 落入 `[...DEFAULT_HOME_LAYOUT, ...items]`，**把建筑重新加回来**——用户删了等于白删。
2. **[中] 复制落位点选在物件上会变成「选中」**：首版脚本在 (790,470) 点击落位，实际点中的是玫瑰本身，复制数量没增加。
3. **[待验] 撤销/重做是否一步一项**：需要用数量变化验证。

#### 第二遍实现（修复 #1/#2）
- 加入 `schemaVersion` 分支（见上）——这是 #1 的实质修复。
- 复制落位改到星球中央偏下 (700,480)，避免点到对象。
- 修改文件：`src/db/schema.ts`、`src/server/layouts.ts`、`src/lib/layout-api.ts`、`src/components/space/SpaceApp.tsx` + 迁移 `0008`。

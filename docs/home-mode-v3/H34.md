### H34 DIY 参数入库 + 服务端校验 + 旧版本默认

- **要求**：DIY 参数纳入布局数据库 schema 版本，服务端校验部位/颜色；保存刷新、跨会话和参观还原，旧版本无配色使用默认。
- **前置依赖**：H28/H29/H32（parts 数据与渲染）。

#### GitHub 候选对比与已读源码
- **three.js `Editor.js`（MIT）**：材质编辑必须能序列化进场景 JSON 才能保存/重开；不可序列化的状态等于没保存。
- 本项目实现要点：`parts` 作为布局项的一等字段进 DB（jsonb 列），并由**服务端**校验部位白名单与颜色格式——客户端可被绕过，校验必须在服务端。

#### 第一遍实现
- `src/lib/home/diy-parts.ts`：**客户端与服务端共用的唯一权威清单**（`DIY_PART_KEYS` + `validateParts()`），避免「前端能选、后端不认」。
- schema：`planet_layout_items` 增 `parts jsonb` 列；迁移 **`0007_handy_gravity`**（已生成并应用）。
- 服务端 `saveDraft`：`clean()` 内调用 `validateParts(kind, parts)`——部位不属于该 kind 或颜色不是 `#rrggbb` 一律 400；`GET`/`INSERT`（草稿与恢复发布两条路径）都带上 `parts`。
- 客户端：`layout-api` 的 `LayoutItem`/`toLayoutItem`/`fromLayoutItem` 补 `parts`；`/visit` 页的 decor 映射也补 `parts`（参观还原配色）。

#### 第一遍审查（主动构造失败）
1. **[严重] 保存后 `parts` 全是空、非法部位也能 200**：实测保存 revision 16 时 `with parts: 0`，而直接 PUT `{parts:{fake:'#fff'}}` 竟返回 **200**。
   **根因**：`/api/planet-layout` 路由的 zod `itemSchema` **没有声明 `parts`**——zod 默认会**剥离未声明字段**，所以 parts 在入口就被丢掉，后端的 `validateParts` 拿到的是 `undefined`，校验形同虚设。
2. **[中] 恢复发布版本的 INSERT 漏改**：`revertLayout` 路径的 INSERT 只补了列没补第 12 个参数（会插错位），本轮一并修正。
3. **[低] 旧数据兼容**：`parts` 为 null 的旧布局项 → 模型用默认色（`PartTint` 无 parts 时不包裹）——符合「旧版本无配色使用默认」。

#### 第二遍实现（修复 #1/#2）
- 路由 `itemSchema` 增加 `parts: z.record(z.string(), z.string()).nullish()`（并注释说明 zod 会剥离未声明字段这个坑）。
- 两条 INSERT 都补齐 `$12` 与参数。
- 修改文件：`src/app/api/planet-layout/route.ts`、`src/server/layouts.ts`、`src/lib/layout-api.ts`、`src/lib/home/diy-parts.ts`、`src/db/schema.ts` + 迁移 `0007`。

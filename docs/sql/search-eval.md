# C3 历史检索50条评测

数据版本：`c3-v1-40000`。日期：2026-11-11（Asia/Shanghai）。独立本机库：`knowverse_search_bench`。

消息 40000 条，词项记录 511480 条。两名模拟用户各10000组问答；共20000组/40000条消息，无真实学生数据。环境：PostgreSQL 16.15 (Debian 16.15-1.pgdg13+2) on aarch64-unknown-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit。

## 方法与范围

40个固定主题产生40条字面查询，另10条使用知识点别名。每条先预热一次，再运行5次；基线与新版使用同一批数据、参数和默认数据库规划。整体P50/P95按各方案250次耗时计算；单条P95在5个样本下等于最大值。先测基线再测新版，缓存、机器负载和规划差异仍会影响结果，不能当生产承诺。

gold结果由单独SQL按字面条件与预先分配的知识点关联计算，不复用新版查询生成器；保存gold结果数、总命中数和前10条结果ID。该数据集全部是有结果的正例，不能单独证明泛化检索质量；无结果、伪通配符、用户隔离等由集成测试覆盖。

## 索引实际使用证据

以下是默认`EXPLAIN (ANALYZE,BUFFERS)`对“索引”查询的摘录，没有禁用顺序扫描或强迫规划器使用索引：

```
                                                                          ->  Bitmap Heap Scan on message_terms mt  (cost=22.93..1102.80 rows=324 width=20) (actual time=0.141..1.064 rows=500 loops=1)
                                                                                ->  Bitmap Index Scan on message_terms_pkey  (cost=0.00..22.85 rows=324 width=0) (actual time=0.087..0.088 rows=500 loops=1)
                                                                                      Index Cond: (term = '索引'::text)
                                                          ->  Index Only Scan using message_terms_pkey on message_terms other  (cost=0.42..4.44 rows=1 width=0) (actual time=0.002..0.002 rows=1 loops=250)
                                                                Index Cond: ((term = wanted.term) AND (message_id = m_1.id))
```

完整计划见 `../test-evidence/search-eval.json`。B-tree来自`message_terms(term,message_id)`主键；pg_trgm GIN也已创建，但当前精确词项查询不要求使用它。

## 实现说明

- 中文按连续文本二元组切分，英文/数字按完整词切分，重复词权重上限8。消息正文与会话标题共同入索引。
- 含连续中文的字面查询先取其中文词项交集，再用完整ILIKE验证字序、数字和标点；不把散落的二元组当作完整短语。多词优先从最少的词项集合开始。
- 无连续中文时保留ILIKE子串召回，并与完整词倒排及知识点名称/别名召回融合。一个字或只有标点时仍可走原有字面匹配；%和_按字面转义。
- 精确匹配优先，倒排次之，知识点语义路径再次之；有多路证据时加分，词频加分有上限。结果按问题ID去重，再按相关性、时间、ID稳定排序。
- 所有候选均关联本人messages，知识点仅用公共或本人拥有的记录；已拒绝标签不参与。日期、知识点与学科筛选继续在候选之后生效。
- INSERT/正文UPDATE触发词项重建，标题修改同步所属消息，删除通过外键CASCADE清理。尚未新增数据库RLS，不把应用过滤当作RLS。

## 复现与交接

`npm run search:install`安装本机草案；`npm run bench:search`在独立库生成数据和证据。压测带数据库防重入锁，准备后执行VACUUM ANALYZE以减少重复生成数据造成的垃圾干扰；应单独运行，不与集成测试并行。

基准测量是数据库查询往返，不包括页面、登录鉴权、运行时表存在检查、标签加载。此次类型检查通过，21个测试文件165个用例全部通过，其中C3新增6例。浏览器界面未单独验收。

A的正式迁移/schema集成、RLS与权限审查，及D2/A6共用数据集仍需队友衔接，见 [交接清单](search-handoff.md)。本轮没有代替队友完成这些任务。

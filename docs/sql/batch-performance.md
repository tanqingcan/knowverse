# 批处理与存储过程性能对比（实测）

> 由 `npm run bench:batch` 于 2026-10-28T10:52:23.791Z 生成；本机 PostgreSQL 16.14，同一连接、同一数据量。
> 数据为合成数据，只用于比较“逐行 vs 集合”的量级，不代表生产环境绝对值。

| 场景 | 逐行/逐次 | 数据库内逐行 | 集合/单次 | 说明 |
|---|---|---|---|---|
| 插入 5000 行 | 1473 ms | — | 21 ms | 应用循环 5000 次往返 vs 1 条 INSERT … SELECT |
| 更新 5000 行 | 4885 ms | 133 ms | 59 ms | 应用逐条往返 / PL/pgSQL 游标 / 一条集合 UPDATE |
| 点查 3000 次 | 561 ms | — | 6 ms | 应用循环逐次往返 vs 一条 WHERE id = ANY($1) |

## 结论

1. **往返次数是主要成本**：应用循环每行一次网络往返，本地也慢一个数量级；一条 `INSERT … SELECT` / `WHERE id = ANY($1)` 把 N 次往返压成 1 次。
2. **逐行 UPDATE 在两个层面都吃亏**：应用逐条 4885 ms → 搬进 PL/pgSQL 游标 133 ms（省掉往返，约 37×）→ 一条集合 UPDATE 59 ms（省掉 N 次执行，再 2.3×），合计约 83×。
3. 集合操作让优化器一次看到全量数据，可以做单次扫描 + 批量写；这也解释了为什么本项目把「结算」「班级统计」「周报」写成 SQL/存储过程，而不是在应用里循环。
4. 不是所有逻辑都该下沉：需要调用外部服务（模型、文件解析）的步骤留在应用层，只在事务边界上保证一致——见 `docs/database-design.md` §7。

```bash
npm run bench:batch -- --rows 50000
```

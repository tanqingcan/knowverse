# 历史问答数据库阶段汇报

适用：下周课堂阶段汇报，约5–7分钟，5页内容提纲与讲稿。本轮不生成PPT，不展开全部产品功能。主线是历史问答如何存得合理、查得正确、查得快。

## 第1页 需求与当前范围 约40秒

展示：历史检索页面截图，可用 [已验收截图](screenshots/acceptance-2026-11-17/09-history-combined.png)。

讲稿：“老师要求个人学习助手既能答疑，也能按时间、关键词和知识点找回历史对话。我们这阶段重点完成了问答持久化、组合检索和原消息定位。今天选数据库这条主线，介绍关系设计、一致性控制和一次查询优化。”

原始依据为《大作业描述261020》第3–4页：多维检索、教材风格E-R图、数据库模式，以及规范化和开发方便性的综合判断。3D等表现层功能不作为本次数据库成果展开。

## 第2页 核心关系 约60秒

展示：局部 [对话E-R图](er/er-2-dialogue.png)。图中若有额外实体，口头只解释下列主线，不展示55张表全图。

|关系|用途|关系约束|
|---|---|---|
|users|身份与归属|用户有多个会话|
|conversations|会话容器|会话属于一个用户|
|messages|会话内问答|会话内seq唯一，回答引用原问题|
|concepts|知识点目录|一条消息可涉及多个知识点|
|message_concepts|多对多标签|区分候选、确认与拒绝|

讲稿：“消息和知识点是多对多，拆成关联表后才能按知识点筛选，而不是在消息里拼接一串ID。资料引用另行绑定版本片段，资料更新不会改写旧引用的位置。”

## 第3页 规范化与开发便利的取舍 约80秒

展示：messages 的两个候选键id、(conversation_id,seq)，以及复合外键(conversation_id,user_id)引用conversations(id,user_id)。

讲稿：“一个会话只属于一个用户，所以消息表的user_id存在冗余。相对组合候选键，user_id只依赖conversation_id，形成部分依赖。我们保留它便于本表权限过滤与时间索引查询，但不能只相信应用填写正确，因此用复合外键保证消息和会话归属一致。”

再举复核例子：“我们发现原文把chunk_id决定quote当作函数依赖，这不符合代码允许的摘录规则。同一片段可以被不同回答摘录不同句子，因此撤回引用表只有1NF的结论。我们也区分了可空UNIQUE、条件唯一索引与全局候选键。”

证据：[范式复核](schema/normalization-analysis.md)、[重新导出的键目录](schema/candidate-keys.md)、`tests/citation-fd.test.ts`。不要再讲全库“46张BCNF”，也不声称已证明全库4NF/5NF。

## 第4页 查询优化与实测 约100秒

展示：[同数据前后对照](sql/history-optimization.md)，只选kv_app的两组代表结果。先解释冷门每用户命中5组、热门命中3000组。

讲稿：“原查询按用户扫描消息后，再检查知识点标签。我们把知识点候选问答提前，并在候选层排除旧回复标签，去重后再连接问答、时间和关键词条件。没有增加索引或改数据库模式。改写前后对照返回行、排序和总数，并以两名用户验证权限隔离。”

|知识点|角色|并发|原查询P95 ms|改写P95 ms|
|---|---|---:|---:|---:|
|冷门|kv_app|1|78.74|4.66|
|冷门|kv_app|4|142.15|5.15|
|热门|kv_app|1|144.00|134.32|
|热门|kv_app|4|273.33|103.82|

热门单并发收益较小，样本不足以证明稳定的微小差异；不要统一宣称固定加速倍数。

测量口径：4万条合成消息，PostgreSQL16，每组预热2次、20请求，并发1或4。kv_app在事务内设置app.user_id，计时包含连接获取、事务和回滚，不含HTTP/浏览器。小样本与缓存会影响数字，不作线上SLA。

不要把此前普通知识点约683ms与本轮冷热数据直接相除计算提升倍数；使用同一组数据中的before/after比较。

## 第5页 已完成与后续计划 约70秒

|已经完成|后续准备做|验收方式|
|---|---|---|
|核心模式与FD复核、键目录修正|逐步补齐可空来源关系的业务FD审阅|说明每条FD适用条件，检查实际约束|
|候选集SQL改写、冷热/RLS/并发对照|更大数据量、不同标签分布及HTTP链路测试|保持结果一致，记录P50/P95、计划、连接池等待|
|消息归属复合外键、RLS回归|评估笔记/记忆等来源归属约束|先核对历史数据与删除语义，再新增迁移|
|干净库检查与outbox积压识别|消费与监控、发布备份恢复演练|不删除事件掩盖积压，记录消费/恢复结果|

讲稿：“下一阶段不再堆功能，主要把数据库论证和应用运行条件补齐。我们会继续核对来源数据的归属约束，在更大或更偏斜的数据上测性能，并补充HTTP链路和运维验证。”

## 演示与问答备忘

1. 演示组合检索，点结果回原会话。使用预置demo数据，提前检查服务与模式。
2. 展示复合外键定义和一张局部E-R图。
3. 展示性能对照表；现场不重跑造数/并发基准，避免占用课堂时间。
4. 被问“为什么不全做到BCNF”：用messages的具体FD、收益和数据库补偿机制回答，不宣称冗余一定带来已实测的JOIN收益。
5. 被问“这是线上性能吗”：说明本机合成数据、2个身份、闭环并发1/4、数据库事务测量；HTTP和真机没有混入数字。
6. 被问“还有哪些未完成”：区分本轮已优化SQL与计划中的规模/HTTP/来源约束/运维工作。

复现：`npm run bench`准备独立knowverse_bench数据，再运行 `npm run bench:history`。后者增加固定冷热标签，仅修改独立基准库，不重置业务库。测试用独立knowverse_test；不要与浏览器演示共用同一个正在reset的库。

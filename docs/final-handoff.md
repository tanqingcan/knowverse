## 我的意见

DeepSeek 的缺口方向基本正确，但完成标准应调整：CI 例子不能直接照抄（无 .env 会丢失角色连接，首次库不存在）；系统目录并未隔离；共享造数文件原本只是词表；旧测试报告与冒烟选择器也已过时。这些已按实际代码修正。

临近交付，保留 2D 星系合适。项目当前更需要稳定演示、统一功能口径、保留证据与远程 CI 通过。不要在这一轮扩大为新的 3D 场景或全面重构。

真正值得后续投入的是**知识点筛选查询**：4 万条合成消息下两轮 P95 约 0.57–0.68 秒；执行计划出现大量候选行过滤/物化。后续先在当前基准里比较候选消息集合 JOIN / EXISTS 改写与复合索引，再决定是否新增迁移。其它四类的本机延迟较低，但班级只有 2 人、未测并发，不能用这些数字做线上承诺。

沙箱用于课程演示已有多层防线和实际回归；面向公网前还应补严格 SQL 解析/函数白名单、速率与资源配额。当前测试是固定案例的证据，不能等同于系统全面安全。

发布前还需在远程 PR 实际跑绿 CI、启用 main 保护、对最终提交打 tag，并在目标环境完成备份/恢复演练。没有执行这些外部动作，不应把 D4 标成“发布已完成”。

业务库还存在从 2026-11-16 起未投递的 `growth.stage_changed` outbox 事件。当前投递目标为服务端日志，应在运行维护时安排消费/监控；本轮保留队列作为真实状态，没有为了让检查零警告而删除事件。

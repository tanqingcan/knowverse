## 三、第三章的写作主线

这一章应能让读者沿着一次真实学习活动找到数据。

“学生上传两讲课件并提问，系统记录回答采用的资料片段；学生确认问题的知识点后，之后能够按知识点找回问答和教材原段。”

核心讲解围绕三条关系链。

1. 教材追溯。materials → material_versions → material_chunks ← message_citations → messages。
2. 知识点定位。concepts ← material_chunk_concepts → material_chunks，以及 concepts ← message_concepts → messages。
3. 学习事实。题目版本 → 作答 → 评价 → 学习证据 → 当前状态与成长事件。

关系链上的箭头在此只表示读图方向。正式图中的基数与外键方向必须按实际模式画。

## 六、函数依赖与范式要重点讲什么

### 1. 主例讲消息表的部分依赖

messages 同时有 id 和 (conversation_id, seq) 两个候选键。业务规定一个会话属于一个用户，因此 conversation_id → user_id。user_id 依赖复合候选键的真子集，关系未达到 2NF。

保留该列的理由是按用户筛选消息及表达本表行权限。复合外键 (conversation_id, user_id) 引用 conversations(id, user_id)，在数据库中保证归属相同。查询方便性可以从代码看出，性能收益须引用同口径对照实验。

### 2. 用宽表说明分解解决的问题

只证明一个简化关系 P(user_id, concept_id, concept_name, stage)。

给定 concept_id → concept_name 和 (user_id, concept_id) → stage，可以拆成知识点投影与用户状态投影。公共属性 concept_id 决定知识点投影全部属性，因此该二元分解无损。上述依赖分别保留在对应投影内。

用更新、插入、删除各一个具体异常解释分解的价值。将投影与实际表的字段对应起来。

### 3. 用引用区别“原文”和“本次选出的摘录”

同一个片段可以支持多条回答，每次引用可摘取不同原句。因此 chunk_id 决定片段完整正文，但 chunk_id 不能单独决定本次 quote。引用表保存选用片段与本次摘录，旧回答固定指向原版本。

### 4. 2NF、3NF 的延伸例子放在有余量时

现有复核文档提供 concepts(id, name, name_norm) 和 concept_aliases 四列投影的分析，涉及应用层名称规范化规则。这些结论带有特定投影和业务依赖集，应先明确规则和候选键。正文主论证优先采用更直观的消息、版本、引用和知识点例子。

范式判断依据业务允许的所有状态，不能只看样本或看到代理主键就定级。派生汇总的“可重算”也不能直接推出本表违反 3NF。

## 八、完整性与事务的例子

| 需要保证的事实 | 现有机制 | 答辩可追问点 |
|---|---|---|
| 消息与会话属于同一用户 | 复合外键 | 为什么只给两个单列外键仍不足以约束这件事 |
| 同一份资料内版本号唯一 | (material_id, version_no) 唯一性，上传时锁资料行 | 并发上传怎样分配版本号 |
| 旧回答引用仍可追溯 | 引用 chunk_id，片段固定属于具体版本，外键保护 | 新版修改原文后旧答案打开哪里 |
| 私有资料隔离 | 请求级用户上下文、SQL 可见条件及相关表 RLS | 用普通应用角色查询是否仍隔离 |
| 同次作答最多一条评价 | evaluations.attempt_id 唯一性，结算锁与事务 | 重复提交和中途失败怎样处理 |
| 向量任务可重试 | (chunk_id, model_key) 主键，分批提交，缺项回填 | 编码服务中断或更换模型怎样恢复 |
| 标签确认不被回填覆盖 | 片段关联独立审核，回填冲突时保留已有记录 | 自动识别和人工确认各负责什么 |

事务只包住必要的数据库读写，解析文件和模型调用在事务外。原件存在文件系统，版本状态记录存储失败，重试可建立新版本。正文应写清数据库事务与原文件写入的具体边界。

## 九、物理存储与查询怎样讲清楚

1. 学生原件存储在 UPLOAD_DIR 下，PostgreSQL 保存所有者、资料版本、相对路径、散列与片段。部署时备份两者。
2. material_chunks 按提取出的文本片段存行。应用层分段保留教材位置，数据库有自己的物理页、行版本和长字段管理。
3. 当前实验实例 block_size 为 8192 字节。一次种子样本里，课件 v1 第 5 张的行版本 CTID 为 (0,11)。CTID 会随更新或移动变化，长期引用使用片段主键。
4. messages 的 (user_id, created_at) B 树服务于用户等值加时间范围或排序。material_chunks 的 GIN 三元组索引用于适用的文本匹配。执行计划还取决于数据量与选择性。
5. 读懂 Index Scan、Bitmap Index Scan、Bitmap Heap Scan 和 Seq Scan。解释索引产生候选、回表读取及过滤的顺序。
6. BUFFERS 中 shared hit 是共享缓冲区命中。磁盘物理读取要结合系统缓存和 I/O 观察，不能直接用 hit 推算磁盘节省。
7. 审计表按月分区。查询范围与分区的实际时区边界对齐后，计划可裁剪其他月份。
8. material_chunk_embeddings 使用 real[] 保存单位向量，在权限及课程范围内精确点积比较。当前实现的索引是关系键和访问路径索引，向量比较的规模代价另由评测说明。
9. TOAST、MVCC 和 WAL 属于 PostgreSQL 提供的存储与事务机制，答辩结合本项目使用它们的方式说明。

可使用“一个回答的引用怎样查回第 5 张幻灯片”作 SQL 示例。图中只摘取真实计划里的必要节点，并解释每个节点的输入与输出。完整性能表和重复采样归第 6.1 节。

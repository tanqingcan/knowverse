我们实现了什么

知屿是一个个人学习助手。它保存课程和知识点、历史问答、资料版本、练习及评价，让学生能找回问过的问题，也能回查掌握阶段依据了哪些记录。

PostgreSQL 16 是我们使用的关系数据库管理系统，16 是版本号。它负责保存数据、执行 SQL、检查表约束和处理事务。我们定义业务表、表之间的关系、访问权限和查询方式。

历史问答为什么要换一种查法

假设用户想找自己关于「内连接」的历史问答。页面的一条结果是一组问答，包含用户提问和它的最新回答。只要问题或最新回答带有目标标签，这组就可命中。被拒绝的标签不参与筛选。

先看数据库怎样找到一组问答。JOIN 按指定的列把两张表的行接在一起。这里用回答的 reply_to_id 找到原问题。一个问题有多次回答时，系统按会话内的序号 seq 取最大的那条。

为什么能省工作？ 原来给所有候选问题配最新回答，再筛标签。改写先从已有标签找出可能命中的问题，只给这些问题配最新回答。命中的组越少，可以跳过的组越多。日期、学科、关键词和用户范围等条件仍按原规则处理，最终排序和分页也保留。

展开 SQL · 和课上学的关键字对应

下面给出简化后的查询片段。qm 代表问题，am 代表它的最新回答，参数 $1 是当前用户，$2 是目标知识点。实际代码还处理多标签、其他筛选条件、排序和分页。

原查询的知识点条件
-- 已为每个问题找到最新回答
-- EXISTS 判断是否至少存在一条标签
EXISTS (
  SELECT 1
  FROM message_concepts mc
  WHERE mc.message_id IN (qm.id, am.id)
    AND mc.concept_id = $2
    AND mc.status <> 'rejected'
)
改写后的候选问题集合
-- kept_tags 已筛目标标签、当前用户，
-- 并已排除指向旧回答的标签
SELECT DISTINCT
  CASE WHEN role = 'user' THEN id
       ELSE reply_to_id END AS question_id
FROM kept_tags;
-- 用这些问题 ID JOIN 消息表，
-- 再取每个候选问题的最新回答

DISTINCT 去掉重复问题 ID。实际 SQL 用一段名为 concept_candidates 的公共表表达式组织这组 ID，并用 NOT EXISTS 判断同一问题是否存在序号更大的回答。上面的顺序解释查询逻辑，每一次实际执行以数据库生成的计划为准。

怎么验证它查得对、查得快

在相同的 4 万条合成消息上，用前后两种 SQL 跑相同条件，同时比较结果行、结果顺序和总数。测量使用本机数据库和应用角色 kv_app，包含数据库事务和权限上下文。

数据库请求的 P95 延迟

P95 可以读作「大约 95% 的请求在这个时间内完成」。每组预热 2 次、测 20 次，并发指同时发出的请求数。坐标统一为毫秒。

数据库怎样保护这些记录

写入时检查用户归属

知道会话 ID 就能找到它的用户。我们仍在消息表保留 user_id，便于按用户过滤和检索。为了约束这份冗余数据，消息上的 (conversation_id, user_id) 必须同时匹配会话表里的 (id, user_id)。例如 C1 属于 U1，如果写入 C1、U2 这对编号，数据库会拒绝。

读取时，行级安全策略根据当前用户限制应用角色可见的行。复合外键检查写入是否合法，行级策略检查这次读取能看到哪些记录。

作答结算一起写入

一次结算会更新作答、评价、证据和当前阶段。数据库把这些写入放进一个事务，中间失败会一起回滚。相同作答并发重复提交，测试确认只产生一条评价和一组证据。

撤销证据时，系统记录撤销时间，按剩余有效证据重算阶段。回查过去时，它只使用当时有效的证据，因此撤销前的记录仍可解释。

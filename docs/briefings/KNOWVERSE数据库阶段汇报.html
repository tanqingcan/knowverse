我们实现了什么

知屿是一个个人学习助手。它保存课程和知识点、历史问答、资料版本、练习及评价，让学生能找回问过的问题，也能回查掌握阶段依据了哪些记录。

PostgreSQL 16 是我们使用的关系数据库管理系统，16 是版本号。它负责保存数据、执行 SQL、检查表约束和处理事务。我们定义业务表、表之间的关系、访问权限和查询方式。

点击一次资料引用，数据库读了哪些记录

举个例子，学生问「为什么把右表条件写在 WHERE 里，左外连接的结果会少几行？」回答正文里出现「资料1」。点击这个编号，系统需要打开这一次回答所用的那个片段，并显示当时的版本和位置。

  1. 后端先找材料。 用提问文字、当前学科或知识点等条件，从用户有权看的课程资料中找出一小组片段。后端给它们编成本轮的「资料1、资料2……」，同时记住每个编号对应的片段 ID。
  2. 生成端选要引用的编号。 真实模型模式由模型选择要引用编号和摘录，演示模式由现有规则生成。后端检查编号是否属于本轮候选且在正文出现，有摘录时还检查它能否在片段原文中找到。这个检查能确认出处，回答的推理是否充分还需要单独核对。
  3. 保存引用联系。 后端把「资料1」翻译成真正的片段 ID，在 message_citations 写一行。比如「回答 A12 引用了片段 P81，摘录是……」。点击引用时用 chunk_id 找到 P81，再沿 version_id 找到那版资料。

标注、引用、评价为什么分开存

① 引用回答「这句话用了哪段资料」

一行把一条回答连到一个资料片段，附上引用编号、顺序和摘录。回答可能引多段原文，一段原文也可能被多条回答引用。

② 标注回答「这条消息讲哪个知识点」

系统用问题和知识点目录匹配，真实模型模式也会参考模型提出的知识点名称。自动匹配先存为候选标签。学生从某个知识点入口提问时，系统会为该问题直接记录当前知识点。用户也可以手动确认、移除或补标签。

状态是具体关联的一列。同一条消息可以从「候选」改为「确认」或「拒绝」。当前历史筛选纳入候选和已确认，排除已拒绝。确认用户提问上的标签可以产生一条「提问」证据。

③ 评价回答「这一次作答结果怎么样」

每次练习先确定题目版本。选择题比较选项，数值题按允许误差判断，SQL 题在独立沙箱中对照提交 SQL 和参考 SQL 的查询结果。开放解释题在真实模型模式按公开评分维度给出评价，演示模式按关键词规则。

作答表存提交的答案，评价表存判题方式、结论、分数和反馈。作答刚开始时可以没有评价，结算时一条作答最多对应一条评价。证据表记录这次活动对学习阶段有什么意义，例如是否使用提示。

究竟要存多少？ 以一问一答、两个引用、一个已确认标签和一个候选标签为例。这个例子会有两条消息、两条引用和两条标签。一份讲义以及它的片段可以供后续回答反复引用。只聊天时没有作答与评价记录，开始一次练习才有一条作答，判题完成后才写评价。

分成多张表是为了让不同事实可以独立变化。改一个标签只更新对应关联。展示时用编号把需要的行连起来，已有正文和资料片段可以重复使用。

历史问答为什么要换一种查法

动画最后一步在「回顾」面板选了「左外连接」知识点。下面把同一个问题放到四组数据里，只按知识点筛选。我们要从 U1 的历史中找出相关问题，每个问题显示一行，旁边配它最近的一次回答。

第一步先读懂一组问答。 Q1 是动画里学生的提问，A11 是第一次回答。这里假设它后来又得到一条新回答 A12。两条回答的 reply_to_id 都等于 Q1。A11 的 seq 是 2，A12 的是 3，因此现在显示 Q1 + A12。知识点名称「左外连接」对应 ID K1，用这个号码去关联表找标签。

然后判断要不要显示这组。 找到 Q1 或 A12 其中一条的有效 K1 标签就够了。即使两条都带同一标签，页面仍然只有一组。旧回答 A11 只用于回顾历史，标签筛选看问题和当前最新回答。

优化只改找候选的顺序。 原查询在这组数据里给四个问题都找了一次最新回答，随后排掉 Q2 和 Q3。新查法先拿到标了 K1 的消息。A21 指向 Q2，但还能找到序号更大的 A22，所以丢掉 A21 这条命中。Q1 和 A12 都指向 Q1，只留下一个 Q1。A41 指向 Q4，因此最后只取 Q1 和 Q4 的最新回答。

新查法仍要检查命中标签的回答是不是最新，但可以跳过根本没有目标标签的大多数问题。目标知识点只有少数问答时，省下的工作更多。日期、学科、关键词、用户范围、排序和分页继续按原规则处理。

展开 SQL · 和课上学的关键字对应

下面给出简化后的查询片段。qm 代表问题，am 代表它的最新回答，参数 $1 是当前用户，$2 是目标知识点。实际代码还处理多标签、其他筛选条件、排序和分页。

原查询的知识点条件
-- 已为每个问题找到最新回答
-- EXISTS 判断是否至少存在一条标签
EXISTS (
  SELECT 1
  FROM message_concepts mc
  WHERE mc.message_id IN (qm.id, am.id)
    AND mc.concept_id = $2
    AND mc.status <> 'rejected'
)
改写后的候选问题集合
SELECT DISTINCT
  CASE WHEN t.role = 'user' THEN t.id
       ELSE t.reply_to_id END AS question_id
FROM message_concepts mc
JOIN messages t ON t.id = mc.message_id
WHERE mc.concept_id = $2
  AND mc.status <> 'rejected'
  AND t.user_id = $1
  AND (t.role = 'user' OR (
    t.reply_to_id IS NOT NULL AND NOT EXISTS (
      SELECT 1 FROM messages newer
      WHERE newer.reply_to_id = t.reply_to_id
        AND newer.user_id = $1
        AND newer.seq > t.seq
    )
  ));
-- 把筛出的 ID 连回消息表，补齐问答

DISTINCT 去掉重复问题 ID。实际 SQL 用一段名为 concept_candidates 的公共表表达式组织这组 ID，并用 NOT EXISTS 判断同一问题是否存在序号更大的回答。上面的顺序解释查询逻辑，每一次实际执行以数据库生成的计划为准。

怎么验证它查得对、查得快

在相同的 4 万条合成消息上，用前后两种 SQL 跑相同条件，同时比较结果行、结果顺序和总数。测量使用本机数据库和应用角色 kv_app，包含数据库事务和权限上下文。

数据库怎样保护这些记录

写入时检查用户归属

知道会话 ID 就能找到它的用户。我们仍在消息表保留 user_id，便于按用户过滤和检索。为了约束这份冗余数据，消息上的 (conversation_id, user_id) 必须同时匹配会话表里的 (id, user_id)。例如 C1 属于 U1，如果写入 C1、U2 这对编号，数据库会拒绝。

读取时，行级安全策略根据当前用户限制应用角色可见的行。复合外键检查写入是否合法，行级策略检查这次读取能看到哪些记录。

作答结算一起写入

一次结算会更新作答、评价、证据和当前阶段。数据库把这些写入放进一个事务，中间失败会一起回滚。相同作答并发重复提交，测试确认只产生一条评价和一组证据。

撤销证据时，系统记录撤销时间，按剩余有效证据重算阶段。回查过去时，它只使用当时有效的证据，因此撤销前的记录仍可解释。
